Context

The platform syncs orders and products across Shopify, Amazon, Etsy, and eBay, and uses different carriers for logistics, including Nova Poshta. We needed data to arrive quickly, but also needed to trust it. Webhooks became the place where performance and security stopped being separate topics.

00 — concept

What is a webhook in practice?

The control flow is inverted: instead of asking constantly, you wait for the provider to call you.

The basic idea

You register a URL with the provider: "When X happens, POST the event data here." After that, the provider decides when to send the request.

Polling is calling the delivery company every 5 minutes to ask if the parcel arrived. A webhook is giving them your number so they call when it does.

  • You control the endpoint URL
  • Provider controls when to fire
  • Payload is a plain HTTP POST with a JSON body
  • Your server must respond with 2xx within a timeout

01 — the problem

Why not just ask the API every minute?

Polling feels simple until rate limits, latency and empty responses start shaping the architecture.

pollingpull model

  • Most responses: "nothing changed" — wasted quota
  • Shopify enforces strict per-minute request caps
  • Nova Poshta: tight limits on tracking lookups
  • Polling faster does not guarantee fresher data

webhookpush model

  • The provider pushes the event when it happens
  • Zero API quota spent polling for updates
  • Nova Poshta: tracking number arrives instantly
  • Requests grow with real events, not with repeated checks over time

02 — authenticity

Can you trust the request that hit your endpoint?

The webhook URL is public. The signature is what separates a real provider event from a random POST request.

Shopifyindustry standard

Shopify signs the raw request body with a shared secret. The result arrives as base64 in X-Shopify-Hmac-SHA256.

import hmac, hashlib, base64 def verify(secret, body, header): computed = base64.b64encode( hmac.new(secret.encode(), body, hashlib.sha256).digest() ).decode() return hmac.compare_digest(computed, header)

Nova Poshtacustom — we proposed it

Nova Poshta's webhook API shipped without authentication. We proposed the same pattern: shared secret, HMAC over the body, signature in a header. It became a production requirement on both sides.

# Contract we defined with NP: # Header: X-NP-Signature # Value: HMAC-SHA256(secret, body) → hex verify_np(NP_SECRET, body, np_sig)

03 — signature logic

Why HMAC and not just Hash(secret + body)?

A hash gives bytes a fingerprint. HMAC proves the sender also knew the shared secret.

Plain hash — easy to misunderstand

# Not a signature sig = sha256(body)

Anyone who changes the body can compute a new hash. It proves the payload has a fingerprint, but it does not prove who created it.

Hash(secret + body) — still a bad custom scheme

# Looks better, but don't invent this sig = sha256(secret + body)

With hash functions such as SHA-256, this pattern can be fragile because of length-extension attacks. The practical rule is simple: use HMAC instead of designing your own signature format.

HMAC — a standard keyed signature

expected = hmac_sha256(secret, raw_body) if compare_digest(expected, received): trust_the_payload()
  • The secret stays on Shopify and on our server
  • Only the computed signature crosses the network
  • Changing one byte in the body changes the signature
  • Without the secret, the attacker cannot produce the same value

Presentation version

HMAC is not about hiding the payload. It is about proving that the payload was signed by someone who knows the same secret.

05 — security depth

Two things HMAC does not solve by itself

A valid signature proves who signed the message. It does not prove that the message is fresh or new.

Replay attack

If a valid signed request is captured and sent again later, HMAC still passes. The signature is real, but the event may be stale or duplicate.

# Prevention: check timestamp + deduplicate age = now() - payload["created_at"] if age > 300: reject() # 5-min window if seen(payload["id"]): reject() # already stored

Timing attack on signature comparison

A naive == can stop at the first mismatched byte. Tiny timing differences may leak how much of the signature was correct.

# Vulnerable — exits early on first mismatch if received == expected: ... # Safe — always takes the same time regardless import hmac if hmac.compare_digest(received, expected): ...

The fix is small: use constant-time comparison, such as hmac.compare_digest, instead of a regular equality check.

06 — AI-era risk

When a webhook wakes up an AI agent

In AI workflows, a valid event can still contain hostile instructions. HMAC proves where the payload came from, not whether the text inside is safe.

GitHub ActionsComment and Control

In 2026, researchers showed that PR titles, issue bodies and comments could hijack AI coding agents running in GitHub Actions. The agents treated attacker-controlled GitHub text as task context, executed tools and leaked credentials through GitHub itself.

Source: Aonan Guan et al., "Comment and Control", April 2026.

Why this belongs in a webhook talk

The dangerous part is automatic activation. A GitHub event fires, a workflow starts, an AI agent reads untrusted text and then acts with the permissions of the automation environment.

AI-era rule

HMAC proves the payload came from the provider. It does not make the payload safe to execute as instructions. If webhook data is later read by an AI agent, treat it as untrusted user content.

Controls that matter

  • Separate data from instructions in prompts
  • Give AI agents least-privilege tokens
  • Do not expose long-lived secrets to agent runtimes
  • Require approval before external writes or tool execution

07 — architecture

Store first, process later

The endpoint should do the minimum: verify the request, save the raw event, and respond quickly.

Why store raw?

A Nova Poshta tracking lookup can take 1–3 seconds. If the endpoint waits for it, the provider may time out and retry. Saving first separates receipt from processing.

Respond in under 5 seconds

Shopify marks delivery as failed if it does not receive a 2xx quickly. Database insert first, queue work later, response immediately.

Why Redis?

Redis gives retries, worker concurrency and queue-depth visibility outside the HTTP request. A slow worker does not block incoming webhooks.

08 — response strategy

Return 200 after the event is safely stored

Once the raw event is saved, a worker failure is an internal processing problem, not a delivery failure.

Why this isn't cheating

The webhook is stored before any business logic runs. If processing fails later, the data was still received. Returning 500 would tell Shopify to retry delivery even though the event is already in our database.

What replaces the lost observability

  • Sentry alert fires on every processing failure
  • Full stack trace with the webhook payload attached
  • Error rate tracked per provider (Shopify / NP)
  • Admin panel shows unprocessed events
  • Cron script monitors queue health

09 — reliability

Shopify doesn't give up after one failure

If a delivery fails, Shopify retries the webhook 8 times over the next 4 hours. For Admin API subscriptions, repeated failures can end in automatic deletion.

Why exponential backoff?

If your server is down, retrying every second makes recovery harder. Backoff gives the receiver time to recover and keeps the sender from wasting delivery attempts.

This is sender self-protection

If the failures continue, Shopify stops retrying. For webhook subscriptions configured through the Admin API, repeated failures can lead to automatic deletion.

Implication for architecture

The store-first + 200 OK pattern keeps the endpoint healthy even when processing is behind. Shopify sees successful delivery, while workers recover separately.

Source: Shopify docs, "Deliver webhooks through HTTPS".

10 — real world

After repeated failures, the subscription can disappear

This is not theoretical. On 2026-05-09, Shopify removed a production webhook after repeated failures.

From: partners@shopify.com · To: developer

Your webhook for products/update at

https://[platform-url]/shopify/webhooks?credentials_id=…&source=Shopify&signature=0476d4ace0d143f…

has been removed on 2026-05-09 12:20:13 UTC because it's failing to return a successful response.

When the issue is fixed, you'll need to re-create your webhook.

For more information, view failed webhook deliveries on your Partner Dashboard.

The URL includes a signed credentials_id, so each merchant has a unique endpoint. When the subscription is removed, that merchant stops receiving product sync events until we re-register it through the API.

What happened

A deployment caused the endpoint to return non-2xx responses long enough for Shopify to keep retrying and eventually remove the webhook subscription. Once removed, it does not return automatically.

How we monitor now

  • Admin panel shows active webhook subscriptions per merchant
  • A cron script runs periodically and compares registered subscriptions against expected ones
  • If a subscription is missing → alert fires, auto-registration triggered
  • The script also checks Redis queue depth for processing lag

Disabling is Shopify's feature

The sender is doing reliability engineering too, just for itself. If our receiver keeps failing, Shopify protects its own delivery system by eventually removing the failing subscription.

11 — reliability

Same event twice. Wrong order. Both at once.

Webhooks are delivered at-least-once, not exactly-once. Arrival order is not always event order.

Out-of-order delivery

Store event_at from the provider payload, not only received_at from your server clock. Sort by when it happened, not when it arrived.

Idempotency — handle duplicates

The same event can arrive more than once. Without deduplication, an order may be processed twice or a product update may create a duplicate record.

# Check before enqueuing wh_id = payload["id"] if already_seen(wh_id): return 200() # idempotent no-op store(wh_id, payload, event_at=payload["created_at"]) enqueue(wh_id)

Four timestamps stored per webhook — full traceability

event_at

When it happened at provider

received_at

When it hit our endpoint

queued_at

When placed in Redis

processed_at

When worker finished

Final takeaway: in production, webhook design is not just an endpoint. It is signature verification, fast acknowledgement, queued processing, idempotency, ordering and monitoring working together.
